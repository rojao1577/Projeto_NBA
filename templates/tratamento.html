1. O campo de data

GAME_DATE chegou como texto (tipo {{ raw_date_type }}, por exemplo "{{ raw_date }}"). Como texto, ele não pode ser ordenado de forma confiável nem decomposto em mês ou dia da semana. Foi convertido com pd.to_datetime(..., format="%Y-%m-%d") para o tipo {{ clean_date_type }}.

Por que informar o formato: sem ele, o pandas tenta adivinhar o formato de cada valor, e em formatos como 04/03/2026 não dá para saber se é 4 de março ou 3 de abril. Com o formato explícito (ano-mês-dia), cada parte tem um papel fixo, e qualquer data fora do padrão gera erro em vez de virar um valor errado em silêncio. Todas as {{ raw_shape[0] }} datas foram convertidas sem erro: o período vai de {{ first.strftime("%d/%m/%Y") }} a {{ last.strftime("%d/%m/%Y") }}.

3. Colunas categóricas e numéricas

O enunciado cita W e L como exemplo de colunas a tratar. Verificando a base, nenhuma conversão foi necessária nelas, e o motivo foi documentado:

  • WL → vitoria: é o resultado do jogo, uma categoria (vitória/derrota), mas já vem codificada como número. Os únicos valores presentes são {% for v in wl_values %}{{ v }}{% if not loop.last %} e {% endif %}{% endfor %} (1 = vitória, 0 = derrota), o formato que um modelo usa.

4. Colunas excluídas para aprendizado de máquina

Um modelo de previsão (por exemplo, prever a vitória a partir das estatísticas do jogo) só deve receber colunas que ajudam a generalizar e que não “entregam” a resposta. Saem {{ excluded | length }} colunas:

{% for col, reason in excluded.items() %} {% endfor %}
ColunaMotivo da exclusão
{{ col }}{{ reason }}

A base para modelos fica com {{ ml_shape[0] }} × {{ ml_shape[1] }}. Os três casos que merecem explicação:

  • Vazamento de dados (data leakage). As colunas acumuladas são atualizadas depois do jogo: as vitórias acumuladas de uma linha já incluem a vitória daquela partida. Um modelo que as recebesse “acertaria” o resultado olhando para a própria resposta, e falharia com jogos novos.
  • Mantidas de propósito: time e adversario. A força dos dois times é informação legítima, conhecida antes do jogo, e manter só um deles seria incoerente. Num modelo, ambos entrariam por one-hot encoding.
  • Redundâncias mantidas. Algumas colunas são combinação exata de outras: rebotes = ofensivos + defensivos; pontos = 2 × arremessos convertidos + cestas de 3 + lances livres; os aproveitamentos são convertidos ÷ tentados. Elas foram mantidas porque são variáveis pedidas no projeto (pontos, rebotes) e porque a escolha entre a total e as partes depende do modelo; num modelo linear, seria preciso tirar uma delas.

Excluir para aprendizado de máquina não é excluir do site: toda a análise usa a base tratada completa, com {{ clean_shape[1] }} colunas. A data, por exemplo, sai do modelo, mas continua nos gráficos e nas tabelas de outliers.

(b) Interpretação

Por que essas decisões

  • A base original nunca é alterada. Todo o tratamento é feito sobre uma cópia, por funções que recebem a base e devolvem outra. Assim qualquer resultado pode ser refeito a partir do arquivo original.
  • Verificar antes de converter. O enunciado sugere tratar W e L como categóricas, mas a verificação mostrou que elas já são contagens numéricas corretas (100% de concordância com o resultado jogo a jogo). Converter sem olhar teria criado um problema onde não havia.
  • Toda transformação acrescenta, nenhuma apaga. A data e o confronto originais continuam na base tratada ao lado das colunas derivadas, então é sempre possível conferir uma com a outra. As exclusões só acontecem na versão para modelos.
